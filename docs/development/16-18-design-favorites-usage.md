### 16.1 목표·디자인 원칙

- 이름: **D02 교통 데이터 저널리즘 포털 + 교통정보 브리핑 혼합형**.
- 우선순위: **저장된 실제 교통 뉴스(근거·본문)**와 **선택된 자동차 경로 교통정보(조회 시각·거리·소요시간·정체·지체 거리 비율)**를 동등하게 강조. 읽는 기사와 연결된 경로를 원클릭으로 지도로 열 수 있도록 기존 F23 연동을 유지.
- 시각 언어: 네이비 내비게이션, 밝은 백색/회색 배경, 절제된 블루 CTA, 기사 헤드라인을 강조하는 편집형 타이포그래피, 데이터 패널 그리드, 지도·차트와 동일한 카드 패턴. 혼잡 색상(빨강/주황/초록)은 **실제 응답의 상태 또는 지표 설명에만** 사용. 모바일은 320·390px, 태블릿 768px, 데스크톱에서 재배열.
- 앞선 생성 이미지 4장은 **미리보기 이미지**이며 웹사이트 동작의 증거가 아님. 이미지에 나왔던 임의 수치·기사·원인·사진·날씨·CCTV·사고/공사·다른 교통수단·AI 생성 표시·기사 수천 건·예측/평소 대비/경로 대안·기사 편집·발행 옵션·SNS 공유 기능 등은 현행 서비스의 사실이나 구현 요구로 확정하지 않음. 디자인 시안 속 타사 뉴스 로고와 출처도 사용하지 않음.
- 현재 서비스 사실 범위: Kakao Local/Mobility 자동차 경로의 **요청 시점 응답**, Supabase에 이미 저장된 기사·경로 스냅샷; 뉴스 본문은 현재 Python 규칙형으로 생성하며 LLM 미사용. 실시간 도시 전체 도로망·전체 서울의 대표 통계·독립 원인 분석·평소 교통 대비 예측은 제공하지 않음.

### 16.3 화면별 와이어 구조(기존 경로 유지)

**홈 `/`:** 공통 상단 메뉴 → 네이비/사진 없는 기본 히어로('서울 도로교통 뉴스 브리핑' 및 실제 정보 범위 설명) → 기존 출발·목적 경로 폼 → 조회 전 설명/조회 후 결과 KPI·도로 상태 표·브리핑 → 3개 대표 경로 비교(명시적 조회 버튼 유지) → `/news` 기사 탐색으로 이동. 뉴스 목록 티저는 기존 공개 API가 화면 부하·오류에서 안전한지 분석 후 2차 승인 대상으로 분리.

**지도 `/map`:** 상단바 → 페이지 제목/저장 기사 안내(쿼리 있을 때만) → `mapRouteForm` 검색 바 → 큰 `#map` Kakao 영역 → `#result`의 기존 요약 및 범례/분석 설명. **기사 저장 당시 값과 현재 재조회 값을 분리**. 초기 진입 때 API 자동 호출하지 않는 F23 계약 유지. F19-A 재사용 경우 캐시/조회 시점 오인 방지는 실제 API 반환 헤더를 읽을지 여부를 프런트 상세 구현 전에 결정.

**뉴스 `/news`:** 상단바 → 헤드라인형 소개 → `#newsSearchForm`·날짜·페이지 → `#historyList` 기사 목록 → 선택 기사 `#newsTitle/#newsLead/#newsBody` 본문·분석 한계 → `#savedArticleRouteList`의 경로별 지도 이동 및 `#routeChart` 비교 그래프 → 기존 `#trafficTrendForm`, `#trafficExportForm` 별도 분석/CSV 패널. 검색 전에 저장 뉴스 0건이라고 오인하지 않도록 빈 상태 메시지 구분.

**관리자 `/admin`:** 로그인 전 별도 히어로와 `#loginForm`; 로그인 뒤 `#adminPanel`에서 3단계 흐름과 `#generateDraftButton`, `#draftPreview`, `#saveDraftButton`, `#savedArticleLink`를 유지. 저장은 관리자 명시 버튼 클릭 이후에만 허용하며 서명된 초안과 사용자가 검토한 본문 값 일치 계약을 변경하지 않음.

## 17. F18 관심 경로·즐겨찾기 — 구현 전 상세 설계 (2026-10-20)

> **진행 상태:** 사용자가 D02 종료 후 F18 진행을 요청함. 현재 단계는 **설계·README 기록만 승인**된 것으로 해석하며, 저장 방식·동작·HTML/JS를 포함한 아래 구현 범위는 사용자 최종 승인 전까지 코드에 반영하지 않음. 브랜치 `kakao`만 사용.

### 17.1 목적과 권장 구현 범위

- 기능 ID F18: **방문자가 자주 사용하는 자동차 경로(출발지·목적지)를 즐겨찾기로 저장하고, 빠르게 기존 경로 조회에 재사용**.
- **1차 권장안: 브라우저 `localStorage` 이용, Supabase DB 변경 없음, 로그인 없음.** 개인의 같은 브라우저·같은 사이트 origin(`http://127.0.0.1:8000`)에서만 보존됨. 다른 PC·브라우저·기기 간 동기화되지 않으며, 브라우저 데이터 삭제/시크릿 모드/스토리지 차단 시 없어질 수 있음. `http://localhost:8000`은 `127.0.0.1`과 저장 공간이 다름.
- 서버 호출 없이 **문자열만 저장**하며, 저장 시 API 자동 호출 금지. '빠른 조회'를 누를 때에만 기존 `/api/route` 조회를 실행하는 방식을 권장. 기존 서버 F19-A 30초 캐시/기사 저장·관리자 API는 변경하지 않음.
- 기존 `/`과 `/map` 두 화면 모두 동일한 즐겨찾기 목록 공유. 특정 경로를 선택하면 두 화면의 `#origin`, `#destination`에 저장 값이 입력되고, 사용자가 기존 조회 버튼을 눌러야 API 호출하도록 권장(불필요한 호출 방지).
- 고정 초기 경로 '서울역→잠실역' 등과 별개이며 **방문자가 직접 저장한 항목만** 즐겨찾기에 표시. 자동으로 검색 기록을 영구 저장하지 않음.

### 17.2 사용자 화면·인터랙션 설계

| 화면 | 표시 요소 | 동작 |
|---|---|---|
| 홈 `/` | 기존 `#routeForm` 바로 아래 **관심 경로** 작은 카드: '현재 입력 경로 저장' 버튼, 즐겨찾기 목록, 초기 빈 상태 안내 | 저장할 때 입력 문자열 검증 → 중복 검사 → 추가. 항목별 '불러오기'·'삭제'. 불러오기는 출발/목적 입력만 채우며 검색 API 호출 없음. 기존 '경로 조회' 버튼은 그대로. |
| 지도 `/map` | `#mapRouteForm` 아래 또는 결과 설명 바로 위 동일 **관심 경로** 카드 | 홈과 저장 내용 공유. 불러오기는 폼 입력만 변경; 기존 '경로 표시' 버튼으로 실제 경로 조회. F23 `article_id/route_index` 저장 기사 패널·수동 현재 조회 구분 유지. |
| 모바일 320/390px | 버튼/항목이 하나의 열로 표시; 긴 지명 줄바꿈, 클릭 영역 유지 | 수평 스크롤이나 지도 위 겹침 방지; 키보드 Tab/Enter 버튼 사용 가능, **노란색/주황색 포커스 외곽선 재도입 금지**. |
| 뉴스 `/news`, 관리자 `/admin` | 이번 1차 F18에서 변경하지 않음 | 기존 기사/인증 흐름 보존. |

권장 문구: '이 브라우저에만 저장됩니다. 다른 컴퓨터와는 동기화되지 않습니다.' 및 '불러온 뒤 경로 조회를 눌러 최신 교통정보를 확인하세요.'

### 17.3 데이터 모델·보안·상태 규칙

- 저장 키 예시: `seoul-traffic-favorites-v1`, 값은 JSON 배열. 각 항목 객체는 `{origin: string, destination: string}`만 포함하고 방문자 개인 정보/로그인 토큰/뉴스 기사 전문/지도 키는 저장하지 않음.
- **최대 10개 항목**. 지명 입력은 앞뒤 공백 제거, 공백만인 입력/2자 미만/예외적으로 긴 문자열(예: 100자 초과) 차단; 기존 HTML 폼과 입력 제약은 구현 때 맞춰 조정. 출발지와 목적지가 같은 문자열이면 저장 거부.
- 동일한 `origin → destination` 조합의 중복 저장 차단(저장 이전 공백 정규화, 대소문자 무관 비교 권장). 역방향은 다른 경로로 취급.
- 사용자 명시 '삭제'는 단일 항목만 제거. 전체 삭제·다른 브라우저 전송·서버 저장은 이번 범위에서 제외.
- DOM에는 사용자 입력을 **`textContent`**로 표시하여 HTML 주입 방지; `innerHTML`에 그대로 넣지 않음. JSON 구조 불량·저장 공간 가득 참·localStorage 차단 시 앱 전체 기능은 계속 작동하게 하고 친절한 상태 메시지 표시.
- 저장 시점 교통정보/시간/거리/혼잡 비율을 즐겨찾기에 캐시하거나 '실시간'이라 표기하지 않음. 항상 기존 사용자의 수동 조회 결과가 출처.

### 17.4 구현 파일·테스트·배포 방법

- 후보: `traffic-api/static/favorites.js` (공통 저장/검증/렌더링 기능), `favorites.css` (D02 계열 카드·모바일 간격), `index.html`, `map.html`, `tests/test_favorites.py`, 루트 README. 실제 파일명은 구현 중 기존 정적 배포 패턴에 맞춰 조정 가능.
- 현재 두 페이지 모두 `id="origin"`, `id="destination"` 입력과 서로 다른 `#routeForm` / `#mapRouteForm` 전송 핸들러를 사용. 공통 스크립트는 DOMContentLoaded 이후 현재 페이지에 해당하는 컨테이너가 있을 때만 초기화하고, 폼 제출을 대체하지 않음.
- 기존 F23 저장 기사 링크 `/map?article_id=11&route_index=2` 진입 시, 처음에는 기사에 저장된 경로가 입력되고 현재 조회는 **버튼 클릭 시에만** 실행. 즐겨찾기 선택으로 입력값을 바꾸더라도 과거 저장 기사 기록 자체를 덮어쓰지 않음.
- 자동 테스트: 정적 제공/폼 ID 및 이벤트 핸들러 보존, 유효/무효 저장, 중복·상한 10개·삭제·오류 저장소, XSS 방어, 홈↔지도 같은 저장 키, 선택 시 자동 API 호출 방지, F23 기존 동작 보존. 가능하면 JS 로직을 브라우저 외부 테스트 가능한 순수 함수로 나눠 실제 동작 단위 테스트 추가.
- Windows 개발 환경 전체 `unittest discover` 직전 기준 **70개 `OK`**. F18을 구현하고 추가된 테스트 결과는 사용자 Windows 실행 이후 기록. Chrome 320/390/768px 및 데스크톱에서 저장·불러오기·삭제·새로고침 이후 유지·같은 브라우저의 홈/지도 간 공유 확인.
- GitHub 커밋은 `kakao`만; 기존 Supabase DB, 기사 #11 등 저장 기사, 백엔드 API, `.env`·키/토큰·`main`은 수정하지 않음.

### 17.5 범위 승인 필요

**이 문서는 F18 설계안이며 실제 코드 변경은 없음.** 권장 범위는 **브라우저당 10개 저장 / 홈·지도에서 공유 / 불러오기는 입력만 채우고 조회는 기존 버튼으로 수동 실행 / DB·계정 동기화 없음**. 이 동작·제약이 괜찮은지 사용자 확인 후 구현·테스트·`kakao` 커밋 진행.

### 17.6 F18 1차 구현 완료 및 Windows/Chrome 검증 대기 (2026-10-20)

- 사용자가 **17.1~17.5 F18 설계안을 명시 승인**함. 승인된 범위로 `kakao` 브랜치에 브라우저 저장소 기반 관심 경로 기능을 1차 구현.
- **신규 `traffic-api/static/favorites.js`**: `localStorage` 키 `seoul-traffic-favorites-v1`, 출발/도착 2~100자·앞뒤 공백 제거, 공백 정규화, 같은 시작·끝 거부, 중복 차단(대소문자 무관), 최대 10개, 개별 불러오기/삭제, 화면 상태 메시지. 저장 불능/잘못된 JSON에서 일반 경로 검색 기능을 방해하지 않도록 예외 처리. 목록은 `createElement`/`textContent`로 출력해 입력 HTML을 해석하지 않음. 기능 내부에서 네트워크 `fetch` 또는 폼 자동 전송 금지. 기존 `/api/route` 조회는 사용자가 기존 버튼을 누를 때에만 실행.
- **신규 `traffic-api/static/favorites.css`**: D02 톤을 유지한 관심 경로 카드·항목 버튼·모바일 600px 이하 세로 정렬. **노란색/주황색 포커스 외곽선 금지** 유지.
- **`index.html`, `map.html` 수정**: 기존 `#routeForm`/ `#mapRouteForm` 다음에 `#favoriteRoutes` 카드 추가. 기존 `#origin`/`#destination` ID·조회 버튼·지도 기사 `article_id/route_index` 로더와 기존 기능 스크립트는 변경하지 않음. 두 페이지 모두 공통 `favorites.js`와 `favorites.css` 링크를 추가해 동일 origin에서 즐겨찾기를 공유.
- 저장 값은 **출발지·목적지만**이며 교통시간/혼잡도/기사 내용/계정 토큰은 저장하지 않음. A/B 두 PC 간 GitHub·Supabase 계정 동일해도 브라우저 저장소는 동기화하지 않음. DB/스키마/백엔드 API·카카오 SDK/캐시/관리자 인증·`main`은 수정하지 않음.

## 18. F19-B 카카오 API 호출량·실패 현황 관리 — 승인 전 설계안 (2026-10-20)

### 18.1 목표 및 현황

- 목표: **실제로 카카오 외부 API로 전송된 요청 수·실패 수를 서버에서 관찰**하고, 관리자가 호출 급증·카카오 API 오류와 캐시 효과를 구분해 확인할 수 있도록 한다. 외부 제공자의 공식 과금/쿼터 조회 기능이 아니며 카카오 개발자 콘솔의 수치와 일치한다고 주장하지 않는다.
- 기존 F19-A: `/api/route`는 서버 프로세스 메모리의 **30초 TTL / 최대 128개** 경로 캐시를 사용. 동일 경로 재조회는 `X-Route-Cache: HIT`, 새 조회는 `MISS`를 반환한다.
- 실제 `app/kakao_api.py`는 **Local 장소 검색 API 2회 + Mobility 자동차 길찾기 API 1회**를 각 경로 조회 시 호출할 수 있음. 중간 실패 시 외부 호출은 1~2회로 끝날 수 있음. `/api/briefing/overview`, `/api/briefing/news` 및 관리자 기사 생성 등의 별도 호출 경로는 `/api/route`의 캐시를 거치지 않을 수 있으므로 **공통 외부 요청 함수 `request_kakao_json` 경계에서 측정**하는 방식이 더 정확하다.
- 현재 코드에 외부 호출량/실패 현황의 집계 저장소·조회 전용 관리 API·화면은 구현되지 않았다. 기존 Windows 전체 **77개 unittest OK**(17.16~17.17)를 회귀 기준으로 한다.

### 18.3 통계 정의 및 예외 규칙

- **외부 API 요청 시도**: 카카오에 HTTP GET을 보내기 직전에 증가. 성공은 HTTP 2xx + JSON object 유효성 검사가 끝난 건, 실패는 타임아웃/HTTP status/연결·JSON 디코딩·응답 구조 이상 건. 장소 결과 0건 또는 길찾기 `result_code` 오류는 **HTTP 통신 자체는 성공**이므로 외부 HTTP 실패와 별도로 **비즈니스 수준 결과 실패** 집계 여부를 구현 시 명확히 구분한다. 제안: 두 종류 카운터를 혼합하지 않고 HTTP 실패와 사용자 경로 실패를 분리.
- **캐시 HIT/MISS**: 사용자 요청이 캐시에서 반환된 경우 HIT, 새로운 외부 조회가 필요한 경우 MISS. 동시 같은 경로 요청은 캐시 잠금 직렬화로 하나의 외부 조회만 수행할 수 있음. 실패 시 캐시에 결과를 넣지 않으며 경로 실패는 별도 집계.
- **측정 시작/초기화**: 서버 프로세스가 시작되어 카운터가 생성된 시각 기준. 0건일 때 HIT 비율은 0% 또는 '집계 없음'으로 표시; 실제 카카오 쿼터 잔량/요금 추정으로 사용하지 않는다.
- **저장 규모/동시성**: API 유형·결과 코드 등 소수의 고정된 범주 카운터만 사용해 메모리 증가를 제한. 비동기 호출을 고려하여 경합 없는 카운터 갱신/스냅샷을 구현. 비밀키, 원시 헤더, 개인별 이동 경로는 저장하지 않는다.
